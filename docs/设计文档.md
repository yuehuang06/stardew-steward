# 星露谷农场管家（Stardew Steward）— 设计文档

> AI Agent 大作业 · Rust 课程 · 2026 秋季学期

---

## 一、痛点分析

### 1.1 场景描述

《星露谷物语》（Stardew Valley）表面休闲，实际是一款高度依赖数值规划的经营模拟游戏。玩家每天需要决定：种什么作物、给谁送礼、去哪个矿层、是否升级工具，还要跨四季筹备社区中心献祭。游戏内容量巨大：

- **作物**：30+ 种，各带季节、生长天数、单收/复收、加工链（酿酒/果酱/腌制）；
- **鱼类**：几十种，各有季节 × 天气 × 时间 × 地点四重约束；
- **NPC**：30+ 位，各有生日 + 最爱/喜欢/讨厌礼物清单；
- **矿洞**：普通矿 120 层 + 骷髅洞穴 + 姜岛火山；
- **社区中心**：几十个献祭包裹，横跨四季收集。

### 1.2 现有工具为什么解决不好

**Wiki 与攻略帖：** 权威但纯百科，不读存档、不个性化、不持续跟踪。玩家需要自己查、自己算、自己判断"此刻该干嘛"。攻略帖大多是 min-max 导向（"必须种草莓、必须酿酒"），给休闲玩家制造焦虑而非帮助。

**存档分析工具（如 Stardew Checkup）：** 能读档生成一次性报告，但没有对话、没有个性化建议、不能持续跟踪、不能执行动作。

**通用 Agent（GPT / DeepSeek / GLM 等）：** 有四个硬伤：

| 硬伤 | 具体例子 |
|------|---------|
| 知识会错/过时 | 实测 GLM-5.2 被问"矿洞有多少层"时回答 100 层（正确是 120 层）；被问鱼类钓点时给出错误地点 |
| 读不到存档 | 不知道玩家现在夏季 22 日、资金 23158g、哪些作物明天成熟，只能给泛泛建议 |
| 无法持续跟踪 | 存档随游戏实时变化，通用 Agent 不会自动感知"你刚赚了一笔钱""好感度变了" |
| 只能"说"不能"做" | 无法读取或修改本地存档，不能把建议落地为行动 |

**"为什么不直接把存档 XML 贴给通用 Agent"的反驳：**

原始存档 XML 约 200KB（~50K token），解析后的结构化 JSON 约 1K token，差 50 倍。且 LLM 从几万行 XML 里挑数据会漏、会错、每次不一致。存档解析器是**确定性提取**，编译期保证字段类型安全，每次结果一样。此外，解析器不只是"给 LLM 看一眼"——它是整个有状态系统的基础设施，支撑持续监听、增量 diff、求解器输入，这些是"一次性粘贴 XML"做不到的。

### 1.3 目标用户

**核心用户：时不时上线的休闲玩家**。他们喜欢星露谷的氛围，但没时间背 30+ 作物收益表、几十种鱼的季节时间地点、30+ NPC 的生日喜好。打开游戏只想问一句"我现在该干嘛"，然后轻松玩一会儿。硬核玩家自己背数据做 Excel，反而不需要这个工具。

### 1.4 本 Agent 的定位

**日级日程顾问**：每次打开游戏前读一次存档，给出全天日程；睡觉后存档更新，自动 diff 生成战报。不需要像 Mod 一样实时监控每一步操作，日级粒度的状态读取恰好覆盖"我今天该干嘛"这个核心场景。

## 二、场景定制方案

以下功能均为"通用 Agent 做不到 / 明显弱于本 Agent"的定制点，也是"场景定制化设计"评分项的得分来源。

### 2.1 存档解析器（领域数据源工具）

**技术实现：** 用 `roxmltree`（DOM 式 XML 解析器）读取星露谷无扩展名 XML 存档文件（~2.9MB），通过路径导航提取关键字段：

- `player/money` → 玩家资金
- `dayOfMonth` + `year` + `currentSeason`（根节点直接子元素）→ 当前日期
- `weatherForTomorrow` + `isRaining` + `isLightning` → 天气
- `dailyLuck` → 占卜频道运气值（按官方 wiki `TV::getFortuneForecast` 分层）
- `player/friendshipData/item` → `key/string`=NPC名, `value/Friendship/Points`=好感度
- `locations/location[name=Farm]/terrainFeatures/item` → `value/TerrainFeature[xsi:type=HoeDirt]/crop` → 作物状态（生长阶段、距成熟天数）
- `locations/location[name=Farm]/objects/item` → `value/Object[name=Chest]/items` → 木箱内物品

**与通用 Agent 的差异：** 通用 Agent 无法访问本地文件系统，也不懂星露谷 XML 的 schema。解析器用 Rust 类型系统保证字段安全访问，输出结构化 JSON（~1K token vs 原始 50K token），每次结果确定性一致。

**已验证：** 真实存档解析出 54 株蓝莓、12 株啤酒花、29 位 NPC 好感度、3 个木箱含 44 件物品、运气 +0.078。

### 2.2 游戏知识库（三层缓存架构）

**技术实现：**

```
第 1 层: data/*.json（手写种子数据）
         crops.json(25种) / npcs.json(29位) / fish.json(26种)
              ↓ 首次启动导入
第 2 层: data/knowledge.db（SQLite，rusqlite 关键词检索）
              ↓ LLM 调 query_knowledge 查这里
第 3 层: fetch_wiki 工具（MediaWiki API 在线搜索）
              ↓ LLM 发现第 2 层查不到时调用
              ↓ 结果可缓存回第 2 层
```

**与通用 Agent 的差异：** 通用 Agent 靠训练记忆报数据，会出错（如矿洞层数、鱼类钓点）。知识库提供**确定性数据**，LLM 查到的是经过验证的结构化信息，不是"凭记忆猜"。

### 2.3 规划求解器（确定性决策）

**技术实现：** 将"今天该干嘛"建模为约束优化问题。`auto_tasks` 模块直接吃 `GameState` + 知识库，自动生成候选任务：

- 扫描 `state.crops` 中 `days_to_harvest == 0` 的作物 → 查知识库获取售价 → 生成"收获"任务（收益 = 数量 × 售价）
- 检查 `state.weather.is_raining` → 非雨天生成"浇水"任务（Must 优先级）
- 查知识库 NPC 生日 → 7 天内有生日的生成"送礼"任务
- `state.daily_luck > 0.07` → 生成"下矿"任务（Could，运气好矿石掉落更多）
- 雨天或运气好 → 生成"钓鱼"任务

然后 `greedy::solve` 按 ROI 排序贪心选择，在时间（14h）和体力（270）约束内输出最优日程。

**与通用 Agent 的差异：** 通用 Agent 靠记忆瞎猜收益和优先级。求解器从真实存档数据**算出**收益——"你有 48 株蓝莓可收 × 50g = 2400g"是确定性计算，不是 LLM 估算。分工是：可形式化的部分用代码保证正确，模糊的部分（用户偏好、主观解释）交给 LLM。

### 2.4 校验闭环（固化流程）

**技术实现：** LLM 输出最终日程后，Rust 校验器用硬编码游戏规则检查：

- 推荐花费 > 玩家资金 → 报错
- 日程总耗时 > 14h → 报错
- 优先级字段不是 must/should/could → 报错
- 无 must 任务 → 报错（至少应有浇水或收获）

校验失败 → 自动拼错误信息回传 Prompt → LLM 重试。**LLM 可能建议冬天种蓝莓，但代码永远不会让它通过。**

### 2.5 结构化输出 + 模板渲染

**技术实现：** 系统提示词指示 LLM 在给日程时输出 `DailySchedule` JSON（含 summary/tasks/total_time/total_cost/total_income/notes）。Agent Loop 收到后：

1. `extract_json()` 从可能包含 ` ```json ... ``` ` 的文本中提取 JSON
2. `serde_json::from_str::<DailySchedule>` 解析
3. `Validator::check()` 校验
4. `schedule::render()` 用 Markdown 模板渲染成表格

**与通用 Agent 的差异：** 通用 Agent 直接输出自由文本，格式不可控。本方案保证日程输出格式一致、可校验、可审计。

### 3.6 数据流

**CLI 模式:**

```
用户在终端输入 "帮我安排今天的日程"
    │
    ▼
main.rs ──创建──► Agent
                    │
                    │  ① build_messages() 截断历史 → LLM API (reqwest)
                    │     (context_length 控制, 保留 system + 最近 N 条)
                    │
                    ▼
                 LLM 决定调用工具
                    │
            ┌────────┴────────┐
            │                 │
      read_save          query_knowledge
      (读存档XML)        (查SQLite)
            │                 │
      parser/save.rs    knowledge/mod.rs
      (roxmltree)       (rusqlite LIKE)
            │                 │
      GameState JSON     知识条目 JSON
            │                 │
            └────────┬────────┘
                     │
               工具结果回传 LLM
                     │
                     ▼
               LLM 生成 DailySchedule JSON
                     │
                     ▼
               Agent Loop 解析 JSON
                     │
                     ▼
               Validator 校验 ──不通过──► 错误回传 LLM 重试
                     │
                   通过
                     │
                     ▼
               schedule::render() ──► Markdown 表格 ──► 用户
```

```
                                    ▼
                          返回 Markdown ──► ChatMessage (Markdown 渲染)
                                           或 ScheduleCard (像素风日程卡片)
```

## 四、技术选型

|------|-----------|---------|
| 存档解析 | `roxmltree` | DOM 式解析，适合 2.9MB 复杂嵌套 XML 的路径导航；流式 `quick-xml` 对 xsi:type 等属性处理更繁琐 |
| 序列化 | `serde` + `serde_json` | Rust 生态标准，derive 宏自动生成，零成本序列化/反序列化 |
| HTTP 客户端 | `reqwest`（rustls-tls） | 纯 Rust TLS 实现，不依赖系统 OpenSSL，WSL 和 Windows 都能编译 |

| 知识库 | `rusqlite`（bundled） | SQLite 内嵌编译，不需要系统安装；LIKE 查询对 25 条数据微秒级 |
| CLI | `clap`（derive） + `rustyline` | 类型安全参数解析 + 行编辑（历史/快捷键） |
| GUI 后端 | `tauri` 2 | Rust 后端，复用核心库；原生窗口，无 Electron 的内存开销；emit 事件驱动 |

### 为什么不用 quick-xml 而用 roxmltree？

存档 XML 使用 `xsi:type` 属性区分 `HoeDirt`/`Grass`/`Tree` 等 TerrainFeature 子类型，且嵌套字典结构很深（`item/key/Vector2/X`）。`quick-xml` 是流式的，需要手动维护状态机处理这种深层嵌套；`roxmltree` 是 DOM 式的，可以直接用 `node.children().find(|n| n.has_tag_name("crop"))` 路径导航，代码更清晰、更不容易出错。对于 2.9MB 的文件，DOM 全量加载到内存的开销可接受（~10MB 峰值）。

### 为什么工具 handler 用异步？

fetch_wiki 需要异步 HTTP 请求。为此 ToolRegistry 的 handler 类型从 `Box<dyn Fn>` 改为 `Box<dyn Fn -> Pin<Box<dyn Future>>>`，所有工具统一异步接口。同步工具（如 read_save）用 `async move` 包装。

### 为什么用 Tauri 而不是 Electron？

Tauri 2 后端是 Rust，可以直接 `use stardew_steward` 引用核心库，无需跨进程通信。Agent 的 `Mutex<Agent>` 直接在 Tauri 的 `AppState` 中管理，invoke 命令直接调用 `agent.run()`，零序列化开销。Electron 需要 Node.js sidecar 进程 + IPC 通信，额外复杂度和内存开销。窗口配置（透明/无边框/置顶/可伸缩）通过 `tauri.conf.json` 声明式配置，无需手写窗口管理代码。

### 为什么用 9-slice border-image？

星露谷是像素风游戏，UI 需要配合游戏美学。9-slice（九宫格）是游戏 UI 的标准切图方式：把一张 27×27 的 PNG 切成 9 块，四角固定大小、四边拉伸、中间平铺，保证任意尺寸下边框不变形。用 Python 脚本生成 PNG 后转 base64 内嵌 CSS，无需外部图片文件，打包简单。三色 3px 边框 + 斜角切边还原了星露谷的木质感窗口风格。
